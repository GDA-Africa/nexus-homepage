NEXUS CLI v1.3 documentation

Everything in one page: the MCP server, the agents system, Chameleon delegation, the v1.3 alignment gate, all 18 commands, and the concepts behind the project brain. ⌘F is your friend.

Installation

$ npm install -g @nexus-framework/cli # or run without installing: $ npx @nexus-framework/cli init my-app

Requires Node.js 20+. Works on macOS, Linux, and Windows. The CLI is published as @nexus-framework/cli under Apache 2.0.

Quick start

$ nexus init my-app # new project, interactive setup $ cd my-app && claude # or codex / cursor, .mcp.json is already there › agent calls nexus_wake → NX-WAKE-7K9F-2026-06-10 › "Synced with the brain. What are we building?"

Already have a project? nexus adopt adds the brain without touching your source code.

nexus mcp v1.0 HEADLINE

Starts the brain MCP server on stdio. Any MCP client gets the project brain as 17 schema-validated tools instead of files it's told to read. Generated projects include this .mcp.json, so Claude Code and Codex connect automatically:

{ "mcpServers": { "nexus-brain": { "command": "npx", "args": ["-y", "@nexus-framework/cli", "mcp"] } } }
  • No daemon, no database. The server is spawned per client over stdio and exits when the client disconnects. Markdown in .nexus/ stays the only source of truth.
  • Validated writes. Write tools reuse the same parser/lifecycle layer as the CLI, malformed plan frontmatter becomes impossible, not just detectable.
  • Protocol-clean stdout. Auto-invoke prompts and update banners are bypassed for this command.

The brain

Every NEXUS project carries a .nexus/ directory, the brain. It is plain markdown: readable by humans, diffable in git, callable through MCP.

.nexus/ ├─ docs/ # 8 structured docs + the two hot files: │ ├─ index.md # PROJECT BRAIN, status, backlog, vital signs, progress log │ └─ knowledge.md # append-only memory, decisions, gotchas, patterns ├─ plans/ # durable multi-step work (+ _active.json pointer) ├─ skills/ # core/ custom/ community/, how YOUR project does things ├─ state/ # session tokens, sensor cache (gitignored) │ └─ chameleon.json# v1.2, generation evidence from the UI handoff ├─ config.json # v1.2, project UI generator preference └─ ai/ # master instructions every agent file embeds

The numbered docs (01_vision → 08_deployment) use YAML frontmatter with a status field. template vs populated, which is how nexus upgrade knows what to refresh and what to preserve.

Plans

Plans are the unit of multi-step work: markdown files in .nexus/plans/<id>.md with frontmatter (id, title, status) and sections (Goal, Why, Acceptance Criteria, Steps, Notes, Evidence). They survive across sessions, agents resume instead of re-deriving.

$ nexus plan new "Add OAuth" --type=feature $ nexus plan start add-oauth $ nexus plan tick add-oauth 2 # or nexus_plan_tick via MCP $ nexus plan done add-oauth --summary "24 new tests"
Rule of thumb: any task with ≥3 steps or that spans sessions gets a plan. On done, the CLI auto-appends to the index Progress Log and nudges for a knowledge entry.

Knowledge base

knowledge.md is append-only project memory. Entries are headed ### [category] Title with categories: architecture, bug-fix, pattern, package, performance, convention, gotcha, integration. Agents scan it before decisions and write to it after discoveries, via nexus_query_knowledge / nexus_add_knowledge_entry in v1.0.

nexus consolidate keeps it useful past 200 entries by generating a categorized summary layer, the raw log is never edited or deleted.

Skills system

Skills are pre-read instruction files that teach agents how this project does things, patterns, anti-patterns, validation steps. Three directories, strict precedence:

  • custom/, yours, created with nexus skill new. Sacred: never touched by upgrades.
  • core/, framework-matched, sourced from the registry, refreshed on upgrade.
  • community/, installed packs, reinstallable.

The registry ships 22 framework-agnostic shared skills, including the MCP-era set: nexus-mcp-usage, nexus-plans-workflow, and brain-aware-ci. Browse them all on the skills registry page.

Two kinds of skill SKILL_SPEC v2

Until v1.3 every skill was reference: consulted before an artifact is produced, answering "how do we do this here?". v2 adds procedure (category: procedure) and integration: a procedure skill is a discipline the agent runs, answering "what do I do now?". An interview, a diagnosis loop, a review pass. The distinction is not cosmetic, a reference skill can be skimmed and partially applied with no harm; a procedure skill that is half-run has not been run. Procedure skills take ## Completion Criteria in place of ## Example.

The invocation axis

Every skill declares invocation: model | user, which decides who may invoke it. It defaults to model when absent, so every pre-v2 skill stays valid and behaves exactly as before.

ValueReachable byRole
modelthe agent or youreusable discipline, keeps rich trigger phrasing so auto-invocation fires
useryou onlyorchestration, a skill that drives a whole session and should never fire mid-task

The invariant: a user skill may invoke model skills, a model skill may invoke model skills, and nothing may invoke a user skill except you. That is what keeps the call graph a DAG rooted at the human, rather than orchestrators recursing into each other and dragging three disciplines into one context.

Writing triggers that actually fire

Triggers are matched against the task by token overlap, ranked best-first, so budget pressure drops the least relevant skill rather than an arbitrary one. Keep them 2 to 4 words, task-level, one per distinct case. A long descriptive phrase like "creating a reusable React component" is valid but will not match a real task string, it costs registry bytes and never fires. nexus skill status now validates every skill against SKILL_SPEC and warns about triggers too long to match.

Agents v1.1 HEADLINE

Brain-grounded role definitions in .nexus/agents/, same ownership model as skills (core regenerated / custom sacred / community installable, precedence custom > core > community). Each agent carries a context recipe (docs, knowledge categories, skills, plan scope), a least-privilege MCP tool allowlist, and a handoff contract. Generated as Claude Code subagents in .claude/agents/; everywhere else, a fenced "Agent Roles" table in the instruction files. Regenerate outputs with nexus agent sync.

AgentRoleMission
nexus-implementerbuildWorks the active plan's next step. Never re-derives an existing plan.
nexus-test-writerverificationThe keystone: detects test setup via sensors; writes tests matching 06_test_strategy.md; asks before scaffolding test infra (never silent); records waivers visibly. Verifies other agents' work, never its own.
nexus-reviewerreviewReviews against recorded conventions, citing knowledge entries. Read-only tool allowlist.
nexus-doc-keeperhygieneProgress log, knowledge entries, doctor triage. The brain stays truthful.

The verification gate (D11)

Plans marked done must carry test evidence or an explicit waiver in their Evidence section, doctor check D11 "Unverified Done" flags violations, and nexus plan done warns on empty evidence. Completion without verification is visible, not impossible.

$ nexus agent list $ nexus agent new migration-runner # custom/, sacred, overrides core by name $ nexus agent sync # regenerate .claude/agents/ + Agent Roles blocks

Chameleon delegation v1.2 HEADLINE

nexus init is the interview; Chameleon (@chameleon-ui-lib/react) is the UI generator. NEXUS resolves your answers into an AppSpec, hands it over, then overlays the brain, tooling, CI, and tests around what Chameleon writes. It is opt-in and never a hard dependency, every project must still build with --ui none.

Turning it on

$ nexus use chameleon # this project $ nexus use chameleon --global # every project $ nexus use none # opt back out $ nexus use --explain # what's active, and which file said so $ nexus init my-app --ui none # override for one run

Resolution order: --ui flag → project .nexus/config.json → global ~/.config/nexus/config.json → none. A saved preference is stated during init, never asked about again.

How the handoff works

  • Resolved from your environment, not bundled: NEXUS_CHAMELEON_BIN → project node_modules/.bin → npx --no-install. Absent, older, or broken, generation falls back to NEXUS and prints the reason.
  • Capability-gated, not version-gated: NEXUS asks Chameleon what it supports and disables unavailable paths, so new Chameleon releases light up new paths without a NEXUS release.
  • Validated before it runs: the AppSpec is checked locally, then again via chameleon new --validate-only, before anything is written.
  • Recorded, not claimed: every --json envelope is written to .nexus/state/chameleon.json as generation evidence.
  • Toolchain merged: NEXUS folds its scripts and devDependencies into Chameleon's package.json, which is what makes the generated lint script actually runnable.
Native targets skip Chameleon deliberately. Its component tree is DOM-bound (Radix, MUI, react-router, Tailwind v4), so an Expo target opts out and says why, regardless of a saved preference. A remembered choice must never produce a project that cannot boot.

Agent block preservation (D12)

CLAUDE.md and AGENTS.md are in the always-replace set, so every init / upgrade / repair rewrote them wholesale, silently deleting the block chameleon agents init splices between its <!-- chameleon:start --> markers. NEXUS now captures that block before regenerating and restores it after; doctor check D12 flags any project where it went missing.

Alignment gate v1.3 HEADLINE

The most expensive failure in a project is not bad code, it is well-built code that answered the wrong question, because the agent inferred an ask instead of resolving it. The gate makes alignment a precondition for feature work: a gated plan carries a recorded interview, or the brain says it does not.

What gates, and what does not

Plan typeGated?Why
featurealwaysNew behaviour has branches to resolve before building.
refactoralwaysScope and the out-of-scope list are the whole decision.
spikealwaysAn unaligned spike answers a question nobody asked.
bugwith --majorA data-loss regression and a typo fix are both bug plans. Only you can tell them apart, so you opt in.
choreneverNo branches.
The gate keys off structural facts, never off your prose. It reads the plan's type and whether its ## Grilling section is filled. Classifying "is this task complex?" from the task string was considered and rejected: D11 v1 already shipped a keyword sniff over agent-written text and it was gameable by exactly the agent it targeted. The agent that would skip alignment is the agent that rephrases the task to dodge the gate.

The grilling record

A ## Grilling section inside the plan itself, not a separate state file. It diffs in git beside the work it aligned, the reviewer sees the questions that shaped the plan, and it travels across sessions with nothing to keep in sync. A gated plan is scaffolded with the section pre-seeded and marked pending, so an untouched template never satisfies the gate.

## Grilling **Ask:** Add per-project skill overrides so a team can shadow a core skill. **Resolved** - Precedence, custom/ wins outright; no section merging. A half-overridden skill is harder to reason about than a replaced one. - Upstream drift, `nexus skill status` reports it; it does not auto-update. **Out of scope** - Section-level overrides, revisit only if whole-file proves too blunt

Where it shows up

  • nexus plan new, warns at creation and scaffolds the pending record.
  • nexus plan start, warns, then proceeds. It never refuses.
  • nexus wake, the handshake prints the gate, so an agent that reads nothing else still sees it.
  • nexus_get_context, returns a gate section and injects the gated skill into skills regardless of trigger match. It is composed before every budget-consuming section and is bounded by construction, so it can be charged against the context budget but never dropped.
  • nexus doctor, check D13 flags a started plan with no record, warn by default and error under --strict.
Nothing hard-blocks, deliberately. An MCP tool cannot compel an agent, and refusing to start a plan would push the work outside the plan, where nothing can see it at all. D13 makes a skipped gate visible after the fact. Same posture as the wake handshake: visible, not impossible. Teams that want the wall get it in CI with doctor --strict.

Declaring your own gate

Any model-invoked skill can gate a class of work. A user skill cannot, by the invocation invariant, a gate is injected by the brain, and the brain is not you.

gate: plan_types: - feature - refactor record: "## Grilling"

Context load (D14)

The other cost nobody was measuring. Every generated instruction file is context load: bytes in the agent's window on every turn, spent whether or not they turn out to be relevant. Unlike a doc reached through a pointer, nothing about the task makes that cost go away.

D14 measures per file, not per project. Six harnesses load six different files, Cursor reads .cursorrules, Claude reads CLAUDE.md, so a session pays for one of them, not their sum. Warns above 10 KB, errors above 16 KB or under --strict, and reports near-identical files as info so you know a hand-edit to one will not reach the others.

We ran it on ourselves first. NEXUS's own generated CLAUDE.md was 13.4 KB: the docs table stated twice, "orient first" stated in three places, and a Workflow section instructing the agent to read four files by hand immediately after telling it to prefer one nexus_get_context call. It is 7.9 KB in v1.3, with reference material moved behind a pointer into .nexus/ai/instructions.md and the critical behaviour still inline. A generator test holds it under 8 KB, so NEXUS's own output can never trip its own check.

Brain-aware CI

Generated workflows include a deterministic brain layer, no LLM anywhere:

  • Brief PR comments: on every pull request, CI runs nexus sync + nexus brief --md and upserts one sticky comment (marker <!-- nexus-brain-brief -->) so reviewers see brain state next to the diff.
  • Doctor gate: nexus doctor --severity=error fails the build on drift errors; warnings inform but never block.
Keep the comment job non-blocking. The brief informs; only the doctor error gate should ever block a merge.

Upgrading to v1.x

$ npm install -g @nexus-framework/cli@latest $ cd your-project && nexus upgrade
  • Adds .nexus/state/, .mcp.json, and the MCP + handshake sections to your instruction files.
  • Nothing is lost: populated docs, knowledge, plans, and session state are always preserved.
  • New commands are no-ops until you use them, v0.3.x/v0.4.x projects keep working as-is.
  • v1.1.3: upgrade and repair now normalize partial manifests first. Projects created by older CLIs, or adopted as backend-only (no frontend framework), no longer render the literal string undefined into generated docs and AI config. If a past upgrade wrote undefined into yours, re-run nexus upgrade to regenerate.
  • v1.3.0: adds the alignment gate (doctor check D13, doctor --strict, plan new --major), the context-load check D14, and SKILL_SPEC v2 (invocation, category: procedure and integration, gate). Generated instruction files shrink from ~13.4 KB to ~7.9 KB on the next nexus upgrade; your custom/ skills and populated docs are untouched. Fully additive: invocation defaults to model, so no existing skill is invalidated and no coordinated registry release is needed. Plans created before v1.3 are classified from their source: field, so the gate applies to them too.
  • v1.2.0: adds nexus use and init --ui (Chameleon delegation), plus doctor check D12. upgrade and repair now preserve Chameleon's agent block instead of overwriting it. Nothing here activates on its own, an upgraded project keeps generating exactly as before until you run nexus use chameleon.
  • v1.4.0: the 17 brain tools behind nexus mcp are now importable directly from @nexus-framework/cli's ./mcp subpath, as native TypeScript. No server process required for a host that wants to call a tool directly. Purely additive, nothing about the MCP server itself changed.
  • v1.5.0: three new doctor checks, D14 (context load, moved here from v1.3's byte budget), D15 (a manifest declaring something the project no longer uses), and D16 (docs and code that have drifted apart). Optional .nexus/harnesses.yml describes the AI setup a project is actually running against, so generated instruction files are sized to fit, and nexus harness verify checks that a local setup is really receiving what was sent, not just assumed to. nexus context "<task>" is new too, the same composed context pack the MCP server returns, without needing a server running.
On v1.1.3 vs v1.2.0. The published 1.1.3 tarball already contained the Chameleon work, it was cut while that work sat under an [Unreleased] heading, so 1.1.3 shipped a feature set its own changelog did not describe. 1.2.0 is the same code under the version it should have carried. Upgrading from 1.1.3 to 1.2.0 changes only the version number.
